# چشم‌انداز پلتفرم دوسویهٔ کاسیو‌پلاس — و حلقه‌های بسته‌شده

**تاریخ:** ۹ آگوست ۲۰۲۶
**وضعیت:** چشم‌انداز + ردیابی شواهد در کد + اولین قدم اجرایی (بستن حلقهٔ بازخورد ابزارها)

---

## ۱. چشم‌انداز (به زبان تمثیل)

کاسیو‌پلاس یک **تیم کوچینگ** است؛ پس پلتفرمش دو سو دارد:

1. **سمت داخلی (مثل Obsidian):** داده‌ها را کنترل می‌کند که به درون خودِ تیم می‌خورد — Knowledge Core (`casio.yaml`)، brain-store، گراف دانش، ممیزی و بررسی انسانی.
2. **سمت مشتری:** افرادی که در حال کوچ‌اند، ابزاری را استفاده می‌کنند که **با دانش هسته و تلاش تیم کاسیو ساخته شده** — کوچینگ، متریک، کمپین، محتوا.

پس کاسیو همزمان در حال **تولید و گردش دانش** است و با این کار همواره مسیر و ابزارهای خودش و ابزارهای مشتریانش را می‌سازد:

```text
Knowledge Core (دانش هسته)
      │  دانش → Agentها (system.md + playbook.md + memory.md)
      ▼
Agentها / Skills / Automation Specs  ← ماشین‌آلات ساخت ابزار
      │
      ▼
ابزارهای مشتری (کوچینگ، متریک، محتوا، کمپین، …)
      │
      ▼
بازخورد میدان (coaching-session، casio-metric، acceptance نتایج)
      │
      ▼
intake → quality → review → version proposal → ادغام انسانی
      │
      └──→ دانش هستهٔ بهتر → ابزار بهتر (حلقه بسته)
```

---

## ۲. ردیابی شواهد در کد (که «هست» ثابت شود)

| ادعا | شواهد در کد |
|---|---|
| Agentها از دانش ساخته می‌شوند | `operator/lib/agent-wiki.ts`: هر Agent از فایل‌های `system.md` + **`playbook.md`** + `memory.md` ساخته می‌شود |
| Agentها کار واقعی می‌کنند | `operator/lib/agents/real.ts`: «Every run() does actual work against a live system — no seeded numbers» + ۱۲+ کانکتور زنده |
| Agentها حین گفتگو ابزار می‌خوانند | `operator/lib/agents/runtime.ts`: `chatTools(): LlmToolSpec[]` |
| ابزارها با حکمرانی ساخته می‌شوند | Automation Spec Registry: `draft → pending_approval → approved → execute` + گیت permission |
| مهارت‌ها دارایی‌اند | `operator/lib/skills-catalog.ts`: SKILL.md ها از دیسک خوانده می‌شوند |
| بازخورد از میدان وارد حلقه می‌شود | `src/quality.ts`: `knownSourceSystems` شامل `coaching-session` و `casio-metric` |
| تغییر دانش فقط انسانی و نسخه‌دار | `src/proposal-store.ts` + `src/audit-store.ts` + ممنوعیت write مستقیم به `casio.yaml` |
| خودِ تمثیل کوچینگ | `operator/lib/personas-seed.ts`: persona «کوچ تحول» — check-in خودکار، churn flag، تبدیل هر تحول به referral |

**نتیجه:** ماشین‌آلات کامل‌اند — سیستم **ژنوم خودسازی** دارد.

---

## ۳. سه «اما» (شکاف‌های واقعی در زمان بررسی)

1. **حلقهٔ بازگشت در «جهت دانش» بسته است، در «جهت ابزار» نه.** بازخورد، پلی‌بوک‌ها را بهتر می‌کند، ولی نتیجهٔ خودِ ابزار سنجیده نمی‌شد تا ابزار بازسازی شود. شاهد: `acceptanceCriteria` در Automation Spec تعریف می‌شود ولی در اجرا هرگز چک نمی‌شد.
2. **«مشتری» یک رکورد است، نه یک سطح.** `learnerId` در `coaching-sessions.json` / `casio-metric.json` هست؛ Bounded Context مستقل برای مشتری (پورتال/API/استقرار جدا) نیست.
3. **ژنوم ≠ ارگانیسم.** توانایی ساختن کامل است؛ اما تا اولین کوهورت واقعی مشتری، این «پتانسیل» است نه «عملیات». (سیستم صادقانه همین را می‌گوید: `cron.ts` می‌گوید runner هنوز با dedicated-host می‌آید؛ هیچ‌چیز ساخته‌نشده را ساخته‌شده نشان نمی‌دهد.)

## ۴. اولین قدم اجرایی — بستن حلقه در «جهت ابزار»

برای اینکه حلقهٔ دوم‌مرتبه (دانش → ابزار → نتیجه → بازخورد) واقعی شود، کوچک‌ترین قدم این بود:

**ارزیابی `acceptanceCriteria` در `automation-run.ts`:**

- بعد از هر اجرای Automation Spec، هر معیار پذیرش **به‌صورت تعیّنی** ارزیابی می‌شود:
  - معیاری که کلید ورودیِ اعلان‌شده (`inputData`) را ارجاع دهد → **passed** اگر مقدار موجود و غیرخالی باشد، **failed** اگر ناقص باشد؛
  - معیاری که به هیچ کلید اعلان‌شده‌ای ارجاع ندهد → **not_verifiable** (ارزیابی معنایی به LLM/انسان واگذار می‌شود — صادقانه برچسب می‌خورد، جعلی «سبز» نمی‌شود)؛
  - خروجی‌ها (`outputData`) هنوز توسط runtime تولید نمی‌شوند → معیارهای ارجاع‌دهنده به خروجی هم **not_verifiable** (در run ثبت می‌شود).
- نتیجهٔ ارزیابی روی خودِ Run ثبت می‌شود: `acceptance: { criterion, status, detail }[]`.
- اگر معیاری **failed** باشد: Run با وضعیت `blocked` و خطای `automation_acceptance_failed` ثبت می‌شود و **یک رکورد بازخورد به صف بررسی مشترک** (`data/feedback-intake.json` — همان صفی که MCP می‌خواند) نوشته می‌شود تا بازبین انسانی آن را ببیند، رد یا تأیید کند و در صورت نیاز پیشنهاد نسخه بسازد.

با این تغییر، چرخه کامل می‌شود:

```text
ابزار اجرا شد → معیار پذیرش سنجیده شد → failed → صف بازخورد (automation-runtime)
     → بررسی انسانی → تأیید/رد → (در آینده) پیشنهاد نسخه → دانش/ابزار بهتر
```

**مسیرهای بعدی (پیشنهادی):**
- P1: ارزیابی معنایی معیارهای `not_verifiable` با LLM (و برچسب صادقانهٔ «ارزیابی‌شده با مدل»).
- P1: سطح مستقل «مشتری» (پورتال/API جدا با مرز داده) — وقتی اولین کوهورت واقعی وارد شد.
- P2: اتصال نتایج ابزار به متریک‌های بازگشت (مثلاً «Action Plan هایی که معیار موفقیت‌شان رد شد → بازخورد به پلی‌بوک کوچینگ»).
